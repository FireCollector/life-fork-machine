# 《人生分岔机》长期完善与优化路线

版本：v1.0  
起点：D01–D26 Demo 已完成，后续使用 TASK 编号  
用途：后续按步骤开发，每完成一步再进入下一步

## 1. 这份路线要解决什么

当前版本已经有一条完整、稳定、可复现的体验链路：约束校准、三条世界线、三幕选择、想法检验、代价报告、七天实验、分享摘要和知乎素材审核。工程基础也不错，规则引擎、Schema、单元测试和端到端测试都已建立。

真正的短板不在页面数量，而在下面四件事：

1. 当前核心体验没有真实 AI 参与。即使关闭 AI，产品仍然完全一样。
2. 知乎内容增强了可信度，但还没有成为不可替代的产品机制。
3. 只有“稳定高薪还是跟领导创业”一个完整场景，任意议题目前只能生成候选框架，不能自动进入完整游戏。
4. 七天实验、产品价值和复用意愿还没有真实用户数据支持。

后续不再以“多堆几个功能”为目标，而是把产品做成一套真正可用的决策演练系统：

> 用户输入一个现实困境，系统从知乎社区经验中找到相关观点和证据，AI 将其整理成可审核的三世界推演，用户在游戏里检验自己的假设，再把结论带回现实做一个小实验。

## 2. 从评分结论得到的产品诊断

评分文档不是后续路线的唯一依据，但它指出了几个值得认真处理的产品问题：

| 当前表现                                      | 它说明了什么                                           | 路线中的回应                                                                             |
| --------------------------------------------- | ------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| 产品闭环、技术质量、交付就绪和 UI/UX 得分较高 | 现有三幕、报告和实验是可继续建设的底座，不需要推倒重来 | TASK-029 保留确定性规则引擎，TASK-035 在其上增加 AI，TASK-046–047 继续提升可靠性和体验   |
| AI 核心真实性为 0                             | 当前只有环境变量和模板预留，AI 没有产生可观察结果      | TASK-029–036 完成真实模型调用、结构化输出、来源追溯、动态叙事和隐藏输入评测              |
| 知乎生态契合不错但并非不可替代                | 现阶段换成别的经验社区，主流程依然成立                 | TASK-032–033 让知乎多观点成为证据结构，TASK-041–042 建立从知乎问题进入、再回到表达的循环 |
| 可拓展性停留在结构层                          | `/topic-lab` 可以生成草稿，但第二个问题不能完整游玩    | TASK-031–037 打通任意议题到 `ScenarioPack`，并交付第二个完整场景                         |
| 用户价值只有概念判断                          | 没有访谈、盲测、复用率或现实行动数据                   | TASK-028 先建立用户证据，TASK-038–040 验证七天实验和长期复盘是否真正被使用               |
| 演示表达稍弱于最有记忆点的作品                | 功能很多，但“一眼能复述的核心画面”还可以更集中         | TASK-027 统一产品表达，TASK-047 根据首次用户测试压缩主路径；不为舞台效果牺牲真实产品逻辑 |

这里最重要的判断是：项目的基础不用重做，下一阶段应集中攻克“真实 AI、多议题和真实使用”三个问题。

## 3. 长期产品原则

- 不预测人生，不输出“成功率”和“最佳选择”。
- AI 必须做可观察的工作，并且确实影响场景、提问、实验或报告。
- 知乎内容要能回到原文，事实、他人经验和 AI 推演必须分开显示。
- 规则引擎负责状态和约束，AI 负责理解、组织与表达，不能让模型随意修改数值。
- 证据不足时允许停下来，不用完整但虚假的故事填空。
- 七天实验要帮助用户获得新信息，不是通关后的装饰。
- 新议题先生成候选版本，通过校验和人工审核后再进入正式体验。
- 医疗、法律、投资等高风险议题需要单独限制，不沿用普通人生选择的处理方式。

## 4. 衡量产品是否真的变好

后续每次迭代至少关注一项结果指标，避免只统计页面和按钮：

| 指标           | 想回答的问题                           | 初期目标     |
| -------------- | -------------------------------------- | ------------ |
| 完整体验率     | 用户能否走完校准、三幕、报告和实验启动 | ≥ 60%        |
| 关键假设识别率 | 用户是否认为系统找到了自己真正担心的事 | ≥ 70%        |
| 行动转化率     | 用户是否愿意启动一个现实实验           | ≥ 40%        |
| 七天记录完成率 | 实验是不是实际可执行                   | ≥ 25%        |
| 来源点击率     | 知乎证据是否真的被用户使用             | ≥ 20%        |
| 结果可信度     | 用户是否能说清报告为何这样生成         | 5 分制 ≥ 4.0 |
| 新议题成功率   | 隐藏议题能否生成合格候选场景           | ≥ 80%        |
| AI 降级成功率  | 模型不可用时主流程能否继续             | 100%         |

这些数值是第一版验证目标，不是永久 KPI。完成真实用户测试后再调整。

# 第一阶段：先证明产品需求和 AI 必要性

## TASK-027｜重新冻结产品定义与成功指标

目标：把项目从“比赛 Demo”改成长期产品，统一后续判断标准。

工作清单：

- [x] 将目标用户缩小到一个清晰群体，例如正在做职业、升学或城市选择的年轻职场人。
- [x] 明确核心任务：用户不是来“算命”，而是找出关键未知并设计低成本验证动作。
- [x] 画出当前用户旅程，标注每一步的输入、输出、情绪和流失风险。
- [x] 为“推演有效”写出可验证定义，至少包含关键假设命中、证据理解和行动转化。
- [x] 将 README、PRD 和产品内文案统一到同一个定位。

交付物：

- `docs/PRODUCT-BRIEF.md`
- 一张当前体验流程图
- 第一版指标字典

验收标准：团队成员能在 30 秒内用同一种说法解释“给谁用、解决什么、为什么要用它”。

## TASK-028｜完成第一轮真实用户研究

目标：验证问题是否真实存在，并找出当前流程最难理解的地方。

工作清单：

- [ ] 访谈至少 8 名近期做过重大选择的人，覆盖选择前、选择中和选择后三种状态。
- [ ] 让至少 5 名未参与开发的人独立体验当前 Demo，全程不讲解。
- [ ] 记录他们原本如何搜知乎、向谁咨询、怎样做决定，以及最后缺的是什么。
- [ ] 检查用户是否理解“三世界”“想法检验”“证据支持/冲突/不清楚”和“七天实验”。
- [ ] 收集放弃节点、误解、最有记忆点的画面和真实复用意愿。
- [ ] 不用“你觉得好不好”作为主要问题，优先观察用户实际点击和复述。

交付物：

- 脱敏访谈记录
- 问题优先级列表
- 当前体验基线数据

验收标准：至少找出 3 个重复出现的真实痛点，并能用用户原话说明为什么值得继续做。

## TASK-029｜定义 AI 与规则引擎的职责边界

目标：在接入模型前先决定哪些工作必须由 AI 完成，哪些结果必须保持确定性。

工作清单：

- [ ] 定义 AI 输入输出契约：议题理解、观点归纳、关键假设、候选行动、实验建议和解释文本。
- [ ] 明确规则引擎继续负责状态变化、数值计算、合法跳转、实验进度和发布门禁。
- [ ] 为每个 AI 输出增加 Zod Schema、来源引用、置信提示、模型版本和生成时间。
- [ ] 定义失败策略：超时、拒答、结构错误、证据不足、来源冲突和敏感议题。
- [ ] 规定哪些内容必须人工审核后才能成为正式 `ScenarioPack`。
- [ ] 建立“AI 生成内容”和“确定性演示缓存”的明确标签，不能混写。

交付物：

- `docs/AI-ARCHITECTURE.md`
- AI 输出 Schema
- 错误与降级状态表

验收标准：删除任意一个 AI 模块时，能明确指出产品少了哪项能力；AI 也无法绕过规则引擎直接改写用户状态。

# 第二阶段：做出真实、可观察的 AI Vertical Slice

## TASK-030｜建立服务端 AI Provider 网关

目标：让项目第一次拥有安全、稳定、可替换的真实模型调用能力。

工作清单：

- [ ] 在服务端建立统一 Provider 接口，不把 API Key 暴露给浏览器。
- [ ] 支持结构化输出、Schema 校验、超时、有限重试和取消请求。
- [ ] 记录 request ID、耗时、模型名、Prompt 版本、Token 用量和失败类型，不记录用户敏感原文。
- [ ] 增加缓存和限流，避免相同输入重复消耗。
- [ ] 配置模板降级路径，并在 UI 明确显示“实时 AI”或“演示缓存”。
- [ ] 为正常、超时、结构错误和 Provider 不可用补充测试。

交付物：Provider 接口、服务端 API、运行日志结构和测试。

验收标准：在有效凭据下连续调用 20 次，结构化成功率不低于 95%；关闭凭据后主流程仍可使用缓存继续。

## TASK-031｜把任意议题整理成“决策简报”

目标：用户输入任意普通生活议题后，AI 能先理解问题，而不是立即编故事。

工作清单：

- [ ] 从输入中提取选项、决策期限、相关角色、不可逆成本、约束和未知项。
- [ ] 识别用户话语里暗含的假设，例如“稳定一定安全”或“熟人一定可信”。
- [ ] 对过于模糊的问题提出 1–3 个必要追问。
- [ ] 判断是否属于高风险或不适合推演的主题，并给出安全处理方式。
- [ ] 允许用户编辑 AI 识别结果后再继续。
- [ ] 保存原问题与修改后的结构，方便后续评估 AI 是否真正帮到用户。

交付物：`DecisionBrief` Schema、议题输入页和确认页。

验收标准：使用至少 20 条未写进代码的议题测试，80% 以上能得到可编辑、无明显臆造的决策简报。

## TASK-032｜升级知乎证据检索管线

目标：让知乎内容从静态素材库变成每个议题都会使用的证据入口。

工作清单：

- [ ] 根据 `DecisionBrief` 自动生成多组检索词，而不是只搜索用户原句。
- [ ] 使用官方能力拉取候选内容，处理分页、配额、超时、缓存和去重。
- [ ] 保存内容 ID、作者、原文链接、发布时间、互动信息和抓取时间。
- [ ] 区分个人经历、观点、方法建议和事实性陈述。
- [ ] 不复制不必要的全文；页面以摘要、引用片段和原文跳转为主。
- [ ] Provider 或知乎接口失败时使用标明时间的冻结快照。

交付物：服务端检索接口、证据缓存和来源管理模块。

验收标准：对至少 10 个不同议题都能返回可追溯结果；重复来源、失效链接和失败状态有明确处理。

## TASK-033｜建立观点与证据的 AI 整理层

目标：把“搜到很多回答”变成对决策有用的观点结构。

工作清单：

- [ ] 提取每条内容的主要主张、成立条件、风险提示和可执行建议。
- [ ] 将近义观点聚合，同时保留少数高质量异议，避免只展示多数意见。
- [ ] 为每个结论保存支持来源，不允许生成无来源的事实性判断。
- [ ] 给出适用边界，例如年龄、家庭责任、行业和现金储备不同可能导致结论失效。
- [ ] 识别来源之间的冲突，不强行合并成一个“综合答案”。
- [ ] 在审核台展示 AI 为什么这样归类，并允许人工修改。

交付物：`EvidenceCluster` Schema、观点簇界面和人工修订记录。

验收标准：随机抽查 30 个观点卡，来源可追溯率 100%；人工审核认为“严重曲解原文”的比例低于 5%。

## TASK-034｜生成可审核的候选 ScenarioPack

目标：第一次让真实 AI 和知乎证据共同产出可玩的候选场景。

工作清单：

- [ ] 由决策简报和观点簇生成三条差异明确的世界线。
- [ ] 为三幕生成动作、直接结果、延迟结果、分岔回声和关键假设。
- [ ] 为每个事实性内容绑定来源，为反事实剧情标注“情景推演”。
- [ ] 自动生成路线相关的七天实验候选，但必须满足时间、预算和退出规则。
- [ ] 运行 Schema、完整性、引用、敏感词、数值边界和重复文本校验。
- [ ] 继续使用人工审核门禁；证据不足时只保存草稿，不允许发布。

交付物：`ScenarioPack v2`、生成 API、审核差异视图和发布版本记录。

验收标准：一个从未预置的新议题能从输入走到候选场景，所有重要事实都有来源，人工可以修改并发布。

# 第三阶段：让 AI 真正进入游戏过程

## TASK-035｜接入动态叙事与针对性追问

目标：AI 不只在后台生成一次场景，而是在用户选择后提供有针对性的回应。

工作清单：

- [ ] 根据当前路线、历史动作和约束生成短叙事，长度和语气受控。
- [ ] 在想法检验前，根据用户选择找出最值得追问的一项假设。
- [ ] 生成“支持、冲突、仍不清楚”三类线索，但不得伪造来源或强制制造反转。
- [ ] 报告说明哪些内容来自规则计算，哪些来自 AI 表达。
- [ ] AI 返回失败时继续使用审核模板，不丢失会话进度。
- [ ] 对相同会话保存生成快照，刷新后不改变已经发生的剧情。

交付物：动态叙事接口、AI 状态标签、生成快照和回退测试。

验收标准：改变用户约束或关键选择后，AI 提问和叙事会产生合理差异；刷新页面后结果保持一致。

## TASK-036｜建立 AI 评测与隐藏输入测试集

目标：不再用“看起来能跑”判断 AI 是否有效。

工作清单：

- [ ] 建立职业、升学、城市、关系与个人项目等议题测试集。
- [ ] 将测试分为公开样例、开发集和隐藏集，避免针对固定句子调 Prompt。
- [ ] 评分维度包括结构完整、证据忠实、路线差异、假设质量、实验可执行和安全性。
- [ ] 对不同 Prompt、模型和参数做版本比较。
- [ ] 增加恶意输入、极短输入、矛盾输入、隐私文本和高风险主题测试。
- [ ] 保存失败案例，后续修复必须加入回归集。

交付物：评测数据集、评分脚本和可查看的评测报告。

验收标准：隐藏集结构成功率达到 80%，事实引用错误率低于 3%，高风险议题不会被普通人生推演流程直接处理。

## TASK-037｜完成第二个真正可玩的完整议题

目标：证明架构不是为创业案例量身定做。

建议第二议题：“继续工作还是辞职准备读研”。它和创业场景共享职业成本，但角色、时间尺度、证据类型和实验动作明显不同，适合检验泛化能力。

工作清单：

- [x] 使用 TASK-031–034 的 `ScenarioPack` 合同、来源结构和审核边界形成初稿，不手工复制第一场景结构。
- [x] 人工审核知乎来源、世界线、三幕选择、假设和实验。
- [x] 为第二场景补齐单元测试和完整 E2E。
- [x] 比较两个场景是否出现相同文案、相同数值节奏和强套模板。
- [x] 首页允许用户选择场景，并保留“输入自己的问题”入口。

交付物：第二个 `ScenarioPack`、场景选择页和验收记录。

验收标准：两条场景都能独立走完整闭环；不看标题也能从角色、冲突、证据和实验上明显区分。

# 第四阶段：把七天实验做成真实产品

## TASK-038｜区分“演示实验”和“真实七天实验”

目标：解决快速推进与真实跟踪混在一起的问题。

工作清单：

- [x] `/demo` 保留快速模拟，并明确标记为演示。
- [x] 普通用户模式按照真实日期解锁每日任务，不能一键伪造七天完成。
- [x] 支持当天完成、跳过、改期和提前停止。
- [x] 每天记录行动、结果、证据类型、感受和下一步。
- [x] 实验结束时回到最初假设，比较开始前后的变化。
- [x] 提供数据导出和删除入口。

交付物：真实实验状态机、日历视图和迁移方案。

验收标准：真实模式无法通过刷新或改 URL 跳过日期；演示模式不产生会被误认为真实记录的数据。

## TASK-039｜让实验根据反馈动态调整

目标：实验不是七张固定任务卡，而是能回应真实进展。

工作清单：

- [ ] 每日完成后判断证据是支持、冲突还是信息不足。
- [ ] 根据缺失信息生成下一天建议，但保留用户手动调整权。
- [ ] 当成本、时间或风险超过阈值时建议缩小实验或退出。
- [ ] 支持“对方不回复”“材料拿不到”“条件突然变化”等真实阻塞。
- [ ] 给出为什么调整的解释，并标明使用了哪些记录。
- [ ] 避免把用户情绪波动直接解释为客观证据。

交付物：实验适配器、调整历史和解释组件。

验收标准：同一实验在不同反馈下产生不同但合理的后续动作；用户能看懂调整依据并撤销。

## TASK-040｜建立长期决策档案与复盘

目标：让产品从一次性体验变成可以回看的决策工具。

工作清单：

- [ ] 保存问题、约束、当时选择、关键假设、现实证据和最终行动。
- [ ] 在 7 天、30 天或用户自定义日期发起复盘。
- [ ] 记录“当时最担心什么”和“后来真正发生了什么”的差异。
- [ ] 支持重新打开旧决策，用新信息创建分支版本。
- [ ] 生成个人决策偏差提示，但不贴人格标签。
- [ ] 允许彻底删除单次记录或全部历史。

交付物：决策档案页、复盘流程和版本关系模型。

验收标准：用户能从一年前的记录看懂当时依据，新增信息不会覆盖旧版本。

# 第五阶段：让知乎成为产品机制的一部分

## TASK-041｜支持从知乎问题或内容链接开始

目标：用户不必重新描述已经存在于知乎上的讨论。

工作清单：

- [ ] 支持粘贴知乎问题、回答或文章链接。
- [ ] 提取主题和可用来源，展示授权范围与失败原因。
- [ ] 从多回答中识别相互支持、冲突和遗漏的观点。
- [ ] 让用户选择“哪个观点最像我”“哪个观点最让我不舒服”。
- [ ] 把所选观点直接带入想法检验和世界线生成。

交付物：知乎链接导入页和观点选择流程。

验收标准：同一议题使用不同知乎回答作为起点，会改变关键假设或实验方向，而不是只换一张引用卡。

## TASK-042｜把用户结果带回知乎表达

目标：让体验形成“阅读社区经验—现实验证—贡献新经验”的循环。

工作清单：

- [ ] 根据用户授权，把推演过程整理成回答提纲，而不是替用户发布答案。
- [ ] 区分可公开内容和隐私内容，默认隐藏收入、家庭和真实姓名。
- [ ] 将引用过的知乎内容整理为可检查的来源列表。
- [ ] 七天实验完成后生成“我验证了什么、还不知道什么”的复盘草稿。
- [ ] OAuth 只在用户主动选择发布或同步时启用，权限最小化且可撤销。

交付物：知乎回答草稿、隐私检查页和可选 OAuth 流程。

验收标准：用户能在发布前逐项确认内容；系统不会自动代发，也不会把私人记录混入公开文本。

## TASK-043｜加入多人视角与可信经验贡献

目标：把个人决策变成可邀请他人补充证据的轻协作流程。

工作清单：

- [ ] 用户可邀请一位家人、同事或朋友只回答一个具体问题。
- [ ] 受邀者只看到必要上下文，不会看到完整私人报告。
- [ ] 区分事实补充、个人观点和情绪支持。
- [ ] 多人意见冲突时并列展示，不用投票强行得出结论。
- [ ] 允许用户把匿名复盘贡献为新的社区经验候选。

交付物：受控分享链接、协作记录和匿名贡献审核流程。

验收标准：权限边界测试通过；受邀者不能访问未授权会话内容。

# 第六阶段：产品化与规模化

## TASK-044｜建立账号、云端会话和隐私中心

目标：支持跨设备使用，同时保持匿名体验可用。

工作清单：

- [ ] 未登录用户仍可本地体验，登录只用于同步和长期记录。
- [ ] 建立用户、会话、场景版本、实验和审核记录的数据模型。
- [ ] 提供数据查看、导出、删除和授权撤销。
- [ ] 对自由文本进行最小化采集与敏感信息提示。
- [ ] 服务端加密保存必要数据，密钥与业务数据分离。
- [ ] 为本地存档迁移到云端设计明确的合并规则。

交付物：后端数据层、登录流程和隐私中心。

验收标准：跨设备恢复成功；注销或删除后数据按策略清理；匿名模式不被强制转登录。

## TASK-045｜建立场景编辑与内容运营后台

目标：新增议题不再需要直接修改 JSON 和源码。

工作清单：

- [ ] 可视化编辑世界线、幕、动作、状态变化、假设和实验。
- [ ] 查看 AI 初稿与人工修改差异。
- [ ] 检查来源失效、引用缺失、重复内容和 Schema 错误。
- [ ] 支持草稿、审核、发布、下线和回滚。
- [ ] 记录每次发布的作者、时间和变更原因。

交付物：Creator Studio、角色权限和场景版本管理。

验收标准：非开发者能独立完成一个候选场景的编辑、校验和发布；旧会话仍使用原场景版本。

## TASK-046｜补齐可观测性、可靠性和安全

目标：真实用户使用时，问题能被发现、定位和恢复。

工作清单：

- [ ] 监控页面错误、API 延迟、AI 成功率、Schema 失败率和降级率。
- [ ] 为核心链路增加 Trace ID，串起检索、生成、审核和运行结果。
- [ ] 对 Prompt 注入、越权读取、恶意链接和超长输入做防护。
- [ ] 增加数据库备份、迁移回滚和数据保留策略。
- [ ] 在弱网、移动端、刷新、多标签页和模型超时条件下做 E2E。
- [ ] 建立状态页和故障处理手册。

交付物：监控面板、安全测试、故障手册和恢复演练记录。

验收标准：核心路径连续运行 100 次成功率不低于 99%；AI 故障不会导致用户会话丢失。

## TASK-047｜完成体验、无障碍与性能优化

目标：让首次使用者不依赖讲解也能完成体验。

工作清单：

- [ ] 根据 TASK-028 的观察缩短首屏和校准流程。
- [ ] 为专业词补充就地解释，删除比赛讲稿式提示。
- [ ] 优化移动端布局、触控区域、长文本折叠和报告阅读顺序。
- [ ] 补齐键盘操作、焦点状态、颜色对比和读屏标签。
- [ ] 控制首屏资源、图表体积和动画开销。
- [ ] 为加载、空状态、失败、恢复和无证据场景统一设计。

交付物：体验走查报告、无障碍检查和性能基线。

验收标准：5 名首次用户中至少 4 名无需帮助走完主流程；移动端无阻断性布局问题。

## TASK-048｜公开部署与持续验证

目标：把项目变成可以长期访问、持续学习的公开产品。

工作清单：

- [ ] 建立开发、预发布和生产环境。
- [ ] 配置域名、HTTPS、环境变量、数据库和健康检查。
- [ ] 发布前自动运行 lint、类型检查、单元测试、E2E 和构建。
- [ ] 只采集完成率、失败点等必要行为数据，并提供隐私说明。
- [ ] 每轮邀请真实用户体验，记录问题、修复结果和指标变化。
- [ ] 建立版本说明、反馈入口和公开 Roadmap。

交付物：生产地址、发布流水线、反馈渠道和版本记录。

验收标准：生产环境连续稳定运行；每次迭代都有用户证据或质量数据说明为什么要改。

# 第七阶段：可选的创新方向

下面几项不应早于 TASK-037。它们有想象力，但也最容易把产品重新做成“AI 功能展览”。只有核心闭环被真实用户验证后再选一项深入。

## TASK-049｜未来自我角色

- [ ] 让不同世界中的“未来自己”根据同一组事实提出不同追问。
- [ ] 每个角色只能引用对应路线的状态和证据，不能凭空知道未来。
- [ ] 重点是暴露价值冲突，不是表演人格或生成鸡汤。

## TASK-050｜对立观点议事桌

- [ ] 从知乎观点簇中选择两种有代表性的不同立场。
- [ ] 两个 AI 角色围绕用户的具体假设追问，所有事实均可回到来源。
- [ ] 用户最后写下自己的判断，AI 只指出遗漏，不替用户投票。

## TASK-051｜个人决策模式回顾

- [ ] 在用户积累多次决策后，分析常见未知、拖延点和验证习惯。
- [ ] 只描述可观察行为，不生成“冒险型人格”等标签。
- [ ] 用户可以纠正系统总结并关闭这项分析。

# 7. 每一步的统一完成条件

以后执行任意步骤，都需要同时满足：

- [ ] 功能已实现，不以静态图片或固定文案代替。
- [ ] 正常、失败和降级状态都能看到。
- [ ] 新逻辑有单元测试，主流程变化有 E2E。
- [ ] `npm run lint`、`npm run typecheck`、`npm test`、`npm run build` 通过。
- [ ] 更新 README、架构或对应产品文档。
- [ ] 没有提交密钥、真实隐私数据或未经授权的知乎全文。
- [ ] 人工检查一次手机和桌面体验。
- [ ] 能用一句话说明这一步改善了哪个用户结果。

# 8. 现在最应该做什么

下一步从 **TASK-027** 开始，不要直接跳去接模型。先冻结产品定义和衡量方法，再通过 TASK-028 找到真实用户的重复痛点。这样 TASK-029–035 接入的 AI 才会服务于用户决策，而不是为了证明项目“用了 AI”。
